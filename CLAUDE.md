## What the system is

A web app where users chat with an AI that keeps long-term memory, organizes work in project workspaces, answers from uploaded documents with GraphRAG (a knowledge graph built from the documents, shown live in the chat screen), and splits complex requests across cooperating agents. Stack: Next.js + React + TypeScript + Tailwind (frontend), FastAPI (backend), LangChain/LangGraph (agents), PostgreSQL + pgvector (only database, including embeddings and the knowledge graph), Redis + Celery (background jobs), Ollama (local model), a separate Node.js + PDFKit service (reports), Docker.

## Architecture (big picture)

Layered client-server design; each layer talks only to its neighbours:

- **Client**: Next.js, talks to the backend over HTTPS REST plus streamed chat replies.
- **Application (FastAPI)**: auth, chat/conversations, memory service, projects/tasks, knowledge base/GraphRAG, agent orchestrator, complexity classifier + model router, routing/execution logger.
- **Background**: a Celery worker (via Redis) runs conversation summarization, the daily confidence-decay job, document indexing, and knowledge graph extraction. A separate Node.js service builds PDFs from validated JSON.
- **Data**: PostgreSQL + pgvector (chunks, entities, relationships, all in tables, no graph database); uploaded files live on local disk and the DB stores only the path.
- **Model layer**: Low-complexity subtasks → local model (Ollama); Medium → smaller cloud model; High → stronger cloud model.

Cross-cutting behaviours that span many files and must stay consistent:

- **Memory lifecycle**: a conversation ends or is idle 30 min → background job summarizes it and extracts facts → each fact is compared (by embedding) with similar stored memories → no contradiction: save with confidence 1.0; contradiction: store a `pending` row in `memory_conflicts`, **pause and ask the user** (keep old / use new / keep both). Memories are never overwritten without user confirmation (BR-3, BR-4); replaced text goes to `memory_versions`. Status values in the database: `current`, `needs_reverification`, `past` (deleting a memory really removes it). A daily job sets `confidence = exp(-DECAY_RATE × days since last_confirmed)` (DECAY_RATE is a setting, starts at 0.01/day); confidence is stored 0 to 1 and shown as a percentage; a memory used in a reply while below 50% becomes `needs_reverification`. Each reply records the memories it used in `message_memories`. Personal and project memory are stored and retrieved separately (top 5 by vector similarity).
- **Routing**: planner splits the request into subtasks → classifier rates each Low/Medium/High (failure or uncertainty ⇒ High) → router picks the model (local unavailable ⇒ smaller cloud; Low/Medium result failing a quality check ⇒ rerun on the stronger model; cloud unreachable ⇒ retry 2×) → reviewer loops with researcher at most 2 rounds → response agent combines. Every subtask/agent step, and every graph-extraction call, is logged with complexity, model, time and estimated cost.
- **Privacy**: every query is scoped to the logged-in user (BR-1, BR-14, BR-18, BR-20, BR-21, BR-23). The admin can manage accounts and see job/error status but can never read memories, conversations, documents or knowledge graphs (BR-25). Graph data is owned by a user (and project) like the documents it came from (BR-27).
- **Auth**: passwords hashed, minimum 8 characters; 5 failed logins in a row locks the account 15 minutes.
- **Documents and GraphRAG** (spec change A19, 2026-11-18; **not built yet**; the open questions were answered in A20, and file and table details are decided when each phase is built): PDF/TXT/MD only, max 20 MB; status Processing → Indexed or Failed (Indexed = chunks and embeddings done, searchable by similarity; PER-7 covers only this). Then a second background job extracts entities and relationships per chunk (LangChain graph transformer, through the classifier and router, each call logged) into `graph_entities`, `graph_relations` and link tables; `documents.graph_status` is Pending → Extracting → Ready or Failed. Answers use GraphRAG, run by LangGraph: embed question → find entities (vector search) → expand 2 steps → collect supporting chunks → answer; documents whose graph is not ready fall back to similarity search. Every answer lists its source documents/sections. The chat screen's right panel has Memories and Knowledge graph tabs; the entities and relationships used light up as events streamed over Server-Sent Events (one POST stream with the answer text).
